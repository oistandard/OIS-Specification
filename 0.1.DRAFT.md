## 1. Introduction

### 1.1 Mission and Overview

OIS defines a common API standard for in-store media execution and measurement
across digital signage, sensors, and retail media orchestration systems.

### 1.2 History of OIS

OIS is a cross-industry initiative formed to reduce proprietary integrations and
enable interoperable in-store media operations.

### 1.3 Version History

The current draft is 0.1. This section will list releases as the spec evolves.

### 1.4 Resources

* Project repository and issue tracker
* Implementation guidance in `implementation.md`

### 1.5 Terminology

* Orchestration: SSP/DSP/Ad Server/RMN systems that decide media delivery.
* Execution: Digital signage and sensor services that run in-store systems.

### 1.6 OIS Real-Time Orchestration API

OIS defines real-time delivery and event streaming through the OIS-Events layer,
including WSS event transport and low-latency orchestration signals.

### 1.7 OIS Display Block List Branch

Reserved for future specification of display-level allow/block lists for
inventory activation and compliance.

## Status

Draft. Not yet approved by the TSC.

## Conformance

OIS-compliant implementations MUST follow the normative requirements in this
specification and MAY include optional extensions as described by each layer.

## Roles and Data Flow

OIS defines a single API standard with optional layer implementation. Execution
systems publish and ingest data to the Orchestration side, and Orchestration
systems deliver media, configuration, or signals back to Execution systems.

* Execution to Orchestration (ingest)
* Orchestration to Execution (delivery)

## Conventions

* All payloads are JSON unless otherwise noted.
* Base URL is defined by the implementing service.
* Timestamps use ISO 8601 / RFC 3339 in UTC.

### Required, Recommended, Optional

Attributes marked as required are those whose omission would break the technical
meaning of an object. Recommended attributes are customary and should be
provided when available. Optional attributes may be omitted; unless a default
is specified, omission implies the value is unknown.

### Extensions

OIS follows the OpenRTB convention that extension fields are carried under an
`ext` object. Implementers SHOULD ignore unknown `ext` fields and unknown
enumeration values to preserve forward compatibility.

### OpenRTB and AdCOM Alignment

Where OIS objects overlap with OpenRTB and AdCOM concepts (e.g., device,
content, location, and enumerations), OIS follows the same naming conventions
and semantic definitions. AdCOM enumerations SHOULD be used where applicable,
and vendor-specific values MAY be added as extensions. OIS-specific layers
(e.g., proof-of-play, sensor events) are additive and are not defined by
OpenRTB or AdCOM.

### Transport and Security

OIS endpoints use HTTPS for REST and WSS for streaming. Implementations SHOULD
use TLS 1.2+ and publish authentication requirements out-of-band or in service
documentation.

### Data Encoding

Servers SHOULD support gzip compression and the `Accept-Encoding: gzip` header.

### Versioning Behavior

OIS is intended to evolve with non-breaking additions. Implementations MUST be
tolerant of new fields and ignore unknown fields when possible.

### Privacy

Implementers are responsible for compliance with applicable privacy laws and
regulations. OIS encourages explicit privacy signaling in layer-specific payloads
when sensitive data could be inferred.

## 2. OIS-Core

### 2.1 Transport

The base protocol for OIS is HTTP over TLS. OIS endpoints use HTTPS for REST
and WSS for streaming. Calls returning content SHOULD return HTTP 200. Calls
returning no content SHOULD return HTTP 204. Invalid requests SHOULD return
HTTP 400.

### 2.2 Security

TLS is strongly recommended for all OIS communications. Authentication and
authorization mechanisms are implementation-specific and MUST be documented by
each service.

### 2.3 Data Format

JSON is the primary data format for requests and responses. Payloads use the
`application/json` content type unless otherwise specified.

### 2.4 Data Encoding

Implementations SHOULD support gzip compression and the `Accept-Encoding: gzip`
header to reduce payload size.

### 2.5 OIS Version HTTP Header

Services MAY include a version header to indicate the OIS version used by the
request or response. If used, the header name is `x-ois-version` and the value
uses the `<major>.<minor>` format (e.g., `0.1`).

### 2.6 Versioning Behavior

OIS intends to evolve via non-breaking additions whenever possible. Implementers
MUST tolerate new fields and enumerations by ignoring unknown values.

### 2.7 Privacy

Implementations are responsible for compliance with applicable privacy laws and
regulations. OIS payloads SHOULD avoid carrying PII and SHOULD indicate
anonymization or aggregation when applicable.

### 2.8 Customization and Extensions

OIS supports vendor-specific extensions via the `ext` object. Extensions MUST
not alter the meaning of existing fields and MUST be safely ignorable.

## 3. OIS-Device

OIS-Device defines a unified inventory model for media players, display surfaces,
and attached peripherals. A device MAY include zero or more outputs and peripherals,
allowing a single device record to represent a standalone media player with
connected displays, an integrated smart display, or a sensor-only device.
